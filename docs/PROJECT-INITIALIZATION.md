# Initialize a project directory

AFD creates a project foundation from a reviewed JSON brief without model calls, skills,
network downloads, or manual editing of generated files. It supports policy-only and
dependency-free Rust workspace recipes. A foundation contains canonical instructions,
engineering guidance, an ADR lifecycle, and optional explicit Apache-2.0 licensing.

Foundation creation and multi-harness activation are separate operations. Selecting a harness
does not establish that it is installed, authenticated, or able to discover project instructions.

## Review and stage

Use the [policy-only brief](../recipes/project-init/policy-only.brief.json) or
[Rust brief](../recipes/project-init/rust-workspace.brief.json) as a starting point. Edit the
brief before planning, especially purpose, selected harnesses, toolchain, components, and
rights holder. The example maintainer is not a legal ownership assertion. The
[schema](../agent-manager/schema/project-brief.schema.json) describes supported fields;
the CLI additionally validates safe paths and unresolved choices.

```powershell
afd project recipes --json
afd project inspect 'C:\code\example' --agents 'codex,claude-code,pi,grok,agy' --json
afd project plan 'C:\code\example' --brief .\brief.json --json > .\plan.json
afd project stage --plan .\plan.json --output .\stage --json
afd project validate --stage .\stage --checks structural --json
```

Inspection and planning write nothing. Stage must be disjoint from the target directory.
Plans bind recipe digest, exact output bytes, existing scoped input bytes, and relevant directory
entries; they work without Git or an initial commit. Changes invalidate the plan. Existing
project-owned files with different content are preserved and block apply. Supply reviewed custom
`files`, including an explicit AGENTS.md replacement candidate, to reconcile source practices;
the initializer never silently merges instructions. `policyClosure` lists additional required
supporting files supplied in `files`. No original document is read or copied implicitly.

The exact desired harness list is preserved. There is no automatic Codex insertion for an explicit
selection. `.afd/project.json` stores portable intent and required policy references, not private
machine paths or activation claims. No skill or MCP configuration is installed.

## Validate and apply

```powershell
afd project validate --stage .\stage --checks build --json > .\validation.json
afd project apply --plan .\plan.json --scope foundation --confirm '<approvalToken>' --json
afd project verify 'C:\code\example' --receipt '<returned-receipt-path>' --json
```

The explicit foundation scope applies the reviewed files even if build prerequisites or harness
activation remain pending. It does not claim full setup success. Structural conflicts always block
apply. Rust build checks use an already-installed exact host Rust toolchain from the Rust toolchain
directory. They run formatting, check, Clippy, and tests in a disposable copy, offline and locked.
Missing toolchain or target linker/SDK is reported as blocked; no installer is invoked. This first
version supports standard rustup toolchain-directory layouts, including the mise Rust backend.
No system-profile changes are performed. Build evidence reports a failure without logging raw
command output that could contain sensitive data.

Receipts and recovery journals live in private AFD state, outside the project. `--state-dir`
selects a dedicated external receipt directory for isolated runs; use the same option for later
verification, status, rollback, and recovery. The directory is permission-restricted on apply.
Do not point it at a shared state directory containing unrelated applications' files.

Apply is idempotent for the same verified receipt. Files become project-owned, not automatically
resynchronized from recipes. No Git init, commit, hooks, push, release, daemon, or global tool
installation occurs. Custom source-file content is explicitly reviewed input, not generated by AFD.

## Activate harnesses and report status

Continue through [the harness workflow](PROJECT-HARNESSES.md) with the same explicit desired set.
For initialized projects, harness plans and disposable tests include the required supporting policy
files. Tests check their exact content as well as canonical discovery. Adapter receipts retain
supporting policy digests. A policy change invalidates the evidence. This proves a bounded read
observation, not that an agent will always follow every instruction.

For initialized projects, new live evidence also binds the process identity/platform and runner
contract. Apply requires evidence no older than 24 hours and re-probes each selected executable's
version. Changed or unavailable runtimes require a fresh test. Existing v1 projects without a
project manifest retain their older bounded evidence semantics.

```powershell
afd project status 'C:\code\example' --receipt '<foundation-receipt>' --json
afd project status 'C:\code\example' --receipt '<foundation-receipt>' --validation .\validation.json --harness-receipt '<harness-receipt>' --json
```

Status distinguishes foundation, validation, and harnesses. Without exact supplied evidence it
reports pending/not-run rather than guessing. Full completion requires passing validation and
matching verified harness receipts for every desired agent. Status uses existing receipt semantics;
historical observations are not continuous monitoring of external executables or authentication.
Re-run probes/live tests after relevant environment changes. No model is called by `project status`.

## Rollback and recovery

```powershell
afd project rollback 'C:\code\example' --receipt '<foundation-receipt>' --confirm '<approvalToken>' --json
afd project recover 'C:\code\example' --receipt '<interrupted-receipt>' --confirm '<approvalToken>' --json
```

Rollback removes only recorded newly created files whose bytes still match and only empty
directories created by that operation. Existing files are never overwritten by initialization.
User edits and dependent harness artifacts block rollback. Recover rolls an interrupted apply
back to its prior state; inspect/re-plan to resume creation. It refuses a still-running owner and
can clear a dead operation lock after checking its PID. Unknown or inaccessible process state
fails closed. Receipts remain as historical evidence after rollback.

## Deterministic smoke test

After building AFD, run:

```text
node scripts/project-init-smoke.mjs
```

The smoke executes the built CLI against new local directories for both recipes: inspect,
deterministic plan, stage, structural validation, apply, exact-byte verification, repeat apply,
honest pending-harness status, rollback, and post-rollback verification. It records evidence
under `output/project-init-smoke/`. It invokes no LLM, repairs no generated files, installs
nothing, and does not claim live agent activation or a Rust executable build.
